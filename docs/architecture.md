# Целевая архитектура

## Принцип

MVP реализуется как **модульный монолит** из двух приложений за единым публичным origin. Это уменьшает операционную сложность, сохраняет чёткие доменные границы и оставляет возможность выделять сервисы позже, когда появится подтверждённая нагрузка.

```text
Браузер
  └─ public origin / reverse proxy
       ├─ Next.js: веб-интерфейс
       ├─ Django + DRF: API, права, статусы, аудит
       ├─ PostgreSQL: источник истины и поиск
       ├─ Redis + Celery: фоновые задачи и outbox
       ├─ S3 storage: документы и изображения
       └─ Yandex Cloud Postbox: email через SMTP
```

## Frontend

- Next.js, React и TypeScript;
- Tailwind CSS и shadcn/ui как адаптируемая основа компонентов;
- дизайн-токены и визуальная система будут добавлены из отдельного дизайн-проекта;
- типизированный клиент генерируется из OpenAPI-контракта Django;
- фронтенд отображает доступные действия, но не определяет права доступа.

## Backend

- Django 5.2 LTS и Django REST Framework;
- кастомная модель пользователя создаётся до первой миграции;
- домены: identity, profiles, organizations, projects, applications, moderation, notifications, media и audit;
- бизнес-статусы — явные state machines; проверки переходов и object-level permissions выполняет сервер;
- OpenAPI — единственный контракт между frontend и backend.

## Доступ и безопасность

- `django-allauth` обслуживает Google и GitHub OAuth, а API — email+пароль и подтверждение email;
- веб-сессия хранится в защищённой `HttpOnly` cookie; токены не хранятся в `localStorage`;
- CSRF, ограниченный CORS, rate limiting и серверная валидация обязательны;
- файлы проходят проверку типа и размера, карантин и антивирусную проверку; доступ выдаётся через ограниченные по времени URL;
- секреты передаются только через окружение и secret storage, не попадают в репозиторий и браузер;
- все чувствительные действия журналируются.

## Данные, поиск и фоновые операции

- PostgreSQL — основной источник истины;
- для MVP используется PostgreSQL Full Text Search и `pg_trgm`, включая проверку реальных русских, английских и транслитерированных запросов;
- Celery выполняет отправку писем, обработку файлов и другие отложенные задания через Redis;
- email ставится в очередь только после успешного commit, с идемпотентностью и обработкой повторов;
- объектные файлы размещаются в S3-совместимом хранилище, метаданные — в PostgreSQL.

## Эксплуатация

- локальная и staging-среды поднимаются Docker Compose;
- production использует Docker, managed PostgreSQL, reverse proxy/CDN и CI/CD;
- обязательны health/readiness endpoints, error tracking, метрики очередей и резервные копии с регулярной проверкой восстановления;
- критические пользовательские пути проверяются API, integration и Playwright E2E-тестами.
